## Plan decisions (where the plan departs from the spec's letter, and why)

- **P1 — the phone layout needs a core change (G9, checkpoint 0).** Phase 3 measured that at 390 px core does not use the spec's authored `mobile` layout: core's fit (`core/reports/lib/table-lines.ts` `fitTable`, lines 568–595) tries an authored arrangement with every line after the first starting at `continuationIndent(levels)` (line 509: `INDENT + (groups + nests) × INDENT − CELL_PADDING/2`, 68 px for the Balance Sheet's four group levels), and the line Current · Prior year · Change (about 327 px at max-content) does not fit in the 390 px view minus 68 px. The fit then falls to `autoLines`, which places **every** column, so a phone shows % change, against spec §3 Phone ("% change is not in the phone layout, so a phone does not show it"). Per the run's rule (core gaps are built in core, never designed around), checkpoint 0 adds **G9 — an authored arrangement gives up indent before it is given up:** when an authored layout's lines do not fit at the full continuation indent, `fitTable` tries the same arrangement again at the indent of one group level fewer, down to zero levels (`continuationIndent({ groups: k, nests: 0 })` for k = levels − 1 … 0), then at indent 0, and uses the first that fits (its `source` is the layout's width name, its `indent` that smaller indent); only when none fits does it fall to `autoLines`. Every row draws its later lines at `layout.indent` already (`ReportRow.tsx:152` `lineStyle`, `ReportTable.tsx:271`), so no row code changes. This is general (no package named), changes only reports whose authored layout failed because of the indent (they now get their authored arrangement instead of automatic lines), and needs no human decision: the spec's phone behavior is decided; G9 is how core delivers it. The Balance Sheet at 390 then draws its mobile layout with its later lines at one level's indent (20 px).
- **P2 — e2e count.** Spec §7 lists 10 items; with item 1 at desktop and phone and item 10 at 1280 and 1024 that is 12 runs, the limit. The plan uses 11: item 9 (phone layout) is the phone run of item 1 (one goal: open and read the report on a phone). Each other item is its own test. The tablet wrap of §3 "Every width fits" is core's fit (one line tried first, then the authored tablet layout at ≥ 600 px): with four max-content figures and a 12-character label floor, one line fits down to about 620 px, so the tablet layout is drawn only in a narrow band that e2e cannot hit reliably. Books pins the authored tablet layout in Go (`TestBalanceSheetDisplay`, Validate accepts it); core's `reports-fit.spec.ts` and `table-lines.test.ts` drive the wrap to an authored tablet layout; e2e 10 asserts the geometry of whichever layout core reports at 1024.
- **P3 — seeded days, not posted ones, for the dated checks.** E2E may not post before mid-2026 and may not depend on the fiscal start month. The seed's `PRIOR_YEAR_SEED` (`lib/trial-balance-fixture.ts:54`: Accounts receivable debit / Consulting income credit 3,000.00, dated S = `${year − 2}-08-15`, `year` the seed year) is the only posted entry on or before S in the e2e book: every other seeded entry is dated in the last twelve months (`seed.ts`; the "Register fiscal year start" entry, `seed.ts:372`, is dated `fiscalYearStart(now, month)`, which is after `now − 12 months` for any start month), and no e2e spec posts before 2026-07-01, which is after S while the seed year is 2028 or earlier. So only figures on days ≤ S are exact: As of `${year − 2}-08-14` shows a book with no posted lines (the no-lines state); As of S shows the seed inside Net income, Retained earnings 0.00 (same fiscal year as the as-of day, whatever the start month); As of S + 12 months (`${year − 1}-08-15`) has Prior year day S, so the **Prior year** column reads Accounts receivable 3,000.00, Net income 3,000.00, Retained earnings 0.00, exactly. The Current column on `${year − 1}` days is never asserted as an exact figure (from 2027 on, other specs' fixed 2026 days such as `GL_DAY_1` fall before it); e2e reads it only relative to its own row (Change = Current − Prior year). That the seed moves into Retained earnings in Current a year later is pinned by the Go test `TestBalanceSheetRetainedEarningsAndNetIncome`, not by e2e. `year` in a test is the browser's year (`browserToday`), the seed's year.
- **P4 — `accountRowLabel`, not `accountLabel`.** The spec names the helper `accountLabel`, but package `books` already declares `var accountLabel` (`server/audit.go:67`, the audit label), so a func of that name does not compile. Checkpoint 1 adds `accountRowLabel(group string) *reports.Node` to `server/report_spec_helpers.go`. If p5-journal-report merges first with its own copy, the rebase keeps one helper under one name (theirs if it compiles beside `audit.go`, else this one, with their call sites moved); never two copies.
- **P7 — exact figures in e2e only where the shared DB cannot move them.** Other workers post dated today on the shared e2e DB and books-settings.spec.ts changes the fiscal start month for a few seconds, so an e2e never asserts a delta of Net income, Retained earnings or a section total between two snapshots. It asserts a figure of a row it owns (an account it created), a relation inside one snapshot (Total Assets = Total liabilities and equity; Change = Current − Prior year on one row), or a P3 day. Each test creates its own accounts; no test uses an account another test created.
- **P5 — core-owned behavior.** Customize, Expand all / Collapse all, the loading, error, timeout and no-access states, Copy link and Save as are core's view, driven by core e2e (`reports-view.spec.ts`, `reports-failure-states.spec.ts`, `reports-share.spec.ts`) and by checkpoint 0's new spec. Books pins what Books owns: its spec (Go tests), its share (`server/report_shares.go`, unchanged), and the outline's numbers in e2e. Gate 2 compares the loading, error, timeout and no-access shots only in checkpoint 0 (scratch route), never on the real route.
- **P6 — the class and kind tables.** `server/report_balance_sheet.go` holds the Books-owned table of spec §5 as `balanceSheetPlacement map[string]placement` (`placement{ClassRank int; Class string; KindRank int; Kind string}`, rank 0 = blank); the `cls`/`knd` column formulas and the class/kind group labels are `case` nodes built from it, in type order of `account_types.json`. A Go test checks every asset, liability and equity type of `account_types.json` is in it and no other type is.
