2. **Human decision (2026-11-19): two stored receivable rows for each application**, both at the apply date: a credit on the invoice's item and a debit on the credit memo's item (spec §4.3). Checkpoint 2 builds `receivableCreditApplicationsSQL`, `refreshReceivableCreditMemo`, the new part of `refreshReceivableInvoice`, and verify and rebuild over three queries. 3. **One dialog, three uses.** `ApplyCreditDialog`, `useApplyCredit` and `applyCreditSchema` take a `CreditApplicationKind` (`VENDOR_CREDIT_APPLICATION`, `CREDIT_MEMO_APPLICATION`) and the fixed side `from: 'credit' | 'document'`. Vendor credit → bills is `VENDOR_CREDIT_APPLICATION` with `from: 'credit'`; credit memo → invoices is `CREDIT_MEMO_APPLICATION` with `from: 'credit'`; invoice ← credit memos is `CREDIT_MEMO_APPLICATION` with `from: 'document'`. Checkpoint 3 builds all of the shared parts for both `from` values (schema, hook, dialog body, texts), and its unit tests cover `from: 'document'`; checkpoint 4 only mounts it on the invoice.
4. **The kind holds no collection object.** A hook that writes or reads applications calls `useStore('books_vendor_credit_applications', 'books_credit_memo_applications')` and picks by `kind.key`. The insert row is made by two typed branches (`if (kind.key === 'vendor_credit') … else …`), so there is no cast and no `any`. A read hook runs one live query for each kind and returns `undefined` from the query function of the kind it does not read.
5. **Application row shape.** `useCreditApplications` gives `{ id, amount, date, documentId, documentNumber, creditId, creditNumber }` for both kinds (today `billId`, `billNumber`). Checkpoint 3 renames the readers of `CreditApplicationRow` (`command grep -rn -E 'billNumber|billId' tinycld/books/components/documents tinycld/books/hooks/useCreditApplications.ts tinycld/books/lib/credit-uses.ts tests/credit-uses.test.ts`); the Pay Bills files that have a `billId` of their own are not readers and do not change.
6. **`ReadFrame` gains `section`.** A kind's `ReadFrame` replaces the read view's `SectionReadFrame` (`components/documents/DocumentReadView.tsx`), so a kind with a `ReadFrame` and a `ReadSection` would lose its section. `DocumentReadFrameProps` gains `section: ReactNode` (the kind's `ReadSection`, drawn by `DocumentReadView`; `null` for a kind without one). Order in a credit's frame: notice, `body`, Applied to block, `section`, dialogs, `stamps`. Order in the invoice's frame: notices, `body`, `section`, dialog, `stamps`.
7. **Where a refusal shows.** A server refusal keyed `invoice`, `bill`, `credit_memo` or `vendor_credit` goes under the Credit to apply cell of the row of the refused insert (`refusedRecordId`; with one insert, that row). Every other refusal (keyed `date`, `amount`, or with no key) goes to the root error of `FormErrorSummary`. This is `applyRefusalTarget(key: string): 'row' | 'root'` in `lib/apply-credit-schema.ts`.
8. **Close-date override.** `applyCreditSchema` takes `hasOverride` (from `useMyCloseOverride`, `hooks/useMyCloseOverride.ts`, as `hooks/useWriteOff.ts` does). The vendor credit's dialog takes the same rule (the server already admits an override there).

The rule becomes kind-aware: `phoneButtonOf(lifecycle, actions, kind)` keeps `apply_credit` in the bar for `vendor_credit` and `credit_memo`, and not for `invoice`, where it is a row of More with its key as the row's `shortcut` text.
