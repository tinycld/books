Paths are relative to the package root. Source lives in `tinycld/books/`. Package files import each other relatively (`../lib/x`), never with `~/tinycld/books/...`. ## Decisions that apply to every checkpoint

- **One sales-document layer, one more kind (spec §3.1).** No refund receipt file copies a layer file, a sales receipt file or a credit memo file. A new kind adds its values to the layer's tables, and the layer gains only what this plan names. `hooks/refund-receipt-data.ts` is one more per-kind data source: its queries are typed by its own collections, it imports every shared helper `hooks/sales-receipt-data.ts` and `hooks/credit-memo-data.ts` import from `hooks/document-data.ts` and `hooks/party-read.ts`, and it declares no helper one of them already has (lesson 8). Before the test run, each rule taken from the sales receipt is checked against this spec and this migration: `refund_from` in place of `deposit_to`, no "Sales deposited to" setting, an empty start message, `customer` optional. The other kinds keep their behavior, test ids, texts and tests; the only edits to their existing tests are a list that gains `refund_receipt`, a call shape that gained or renamed a field, and the two changes this plan names (`creditMemoStatus` "Refunded"; the credit memo's void and correction rules).
- **Plan decisions the spec leaves open, or where the reference and the spec differ** (ledger phase 3 and the pass 2 hand-back, settled here):
  - *The form's link row sits between the band's first row and the date row.* The reference (`from-sales-receipt-*`, `payout-*`) draws the link row after Refund date and Tax. Spec §3.4 puts both Tab stops before Refund date, and the Tab order is the DOM order on web and the focus order on native. So the build draws the row between the band's first row (Customer, Bill to, Email) and the date row, as the credit memo's link row is drawn today (`DocumentForm.tsx` `FORM_BAND_ROW_BEFORE = 'date'`). Gate 2 judges the row's look, not its place against the reference.
  - *Band with a link row and a ruled Payment row together (checkpoint 4).* Today `DocumentBand` cuts the band once: at `date` for a kind with a `FormBandRow` (no rule), else at `bandSplitAt` (ruled). A kind with both gets three parts: the fields before `date`, the `FormBandRow`, the fields from `date` up to `bandSplitAt` (unruled, test id `<testId>-band-dates`), and the fields from `bandSplitAt` on as the ruled row `<testId>-payment` (`mt-4 border-t border-border pt-4`). A kind with only one of the two keeps today's band. In checkpoint 3 the refund receipt has no `FormBandRow`, so its band is the sales receipt's.
  - *Payout notice.* No shared inline notice exists (`DocumentNotice` is the full-screen notice). Checkpoint 4 creates `components/documents/DocumentInlineNotice.tsx` (`DocumentInlineNotice({ testID, message })`: a `View` `rounded-lg border border-border bg-background px-3 py-2` with a `Text` `text-sm text-muted-foreground`), drawn inside the link row under the link.
  - *Payout Customer.* Drawn as the disabled Customer picker, out of the Tab order (`tabIndex={-1}`, lesson 19), with no "Edit customer" link change.
  - *Credit memo totals order.* Spec §3.12 wins over the reference: Subtotal, tax, Total, "Credit amount", then **Refunded** and **Unapplied credit**. `DocumentTotalsPanel` draws a kind's `readTotals` rows before the last row today; `DocumentTotalsView` gains the optional `afterLast?: DocumentTotalRow[]`, drawn after the last row with the rows' own style, and the credit memo's rows go there. The vendor credit keeps `after`. Gate 2 judges the two rows' look, not their place against `credit-memo-read-*`.
  - *Read view band.* The source link is a row of the read band above the ruled Payment row (reference `posted-*`, `payout-read-*`). The kind's `ReadBandRow` is one component that draws both.
  - *Two read actions on R.* `DOCUMENT_READ_LABELS` holds one label for each action, so "Refund" (sales receipt) and "Refund credit" (credit memo) are two actions, `refund` and `refund_credit`, both with key `r`. No read view offers two actions on R.
  - *Error states* (reference `errors-*`, `payout-errors-*`): Refund from shows the Balance line and the field error together; the summary holds only the root refusal; the lines error draws under the table; a link refusal draws under the link row.
  - *Two optional hooks on `salesDocKind`, not one.* Spec §4.3 names `PostingLines`. The payout also rebuilds its credit memo's cash-basis rows, and those read the refund's posted entry (`postedPaymentsOf`), which exists only after `postDocument`. So the kind also gains `AfterPost func(tx core.App, doc, original *core.Record) error` (nil for every other kind), run in `postSalesDoc` after the original is voided and before `rebuildCashBasisOf`. A void uses the existing `Withdraw` hook.
  - *`books_refund_receipt_credits` has a `position` column* (number, onlyInt, always 0). `paymentLines` (`server/document_balance.go`) sorts a payer's rows by `position,id`, and spec §4.3 says that file's functions do not change.
  - *A refund's source rows are read with the record, not with `useRecord`.* The record query materializes `salesReceiptRow` and `creditMemoRow` (number, status, and the memo's `balance`, `date`), and a new form reads its source through the screen's source read. Both are part of the screen's loading state and Retry; `useRecord` has no error state (memory p2-tax-rates). Spec §4.5 names `useRecord`; the read is the same row.
  - *One source link in the layer (checkpoint 4, lesson 8).* The credit memo's invoice link is today a special case of the layer (`invoiceLink`, `invoiceSource`, `fromInvoice`, the `invoice` column in `useDocumentSave`, the `cannot-credit` state). The refund receipt adds two more sources, so checkpoint 4 turns the special case into one kind-driven source link (names below) and moves the credit memo onto it with its behavior, texts and test ids unchanged.
  - *The section has no loading row.* A linked-documents section draws nothing while its read loads, as when there is no row; a failed read shows its notice with Retry inside the section (the invoice's Credit memos section does this today).
  - *Linked rows.* A draft refund has no number: its link reads `Draft`. Amounts in the two sections show with no minus sign (the section's heading says what they are); the Sales lists and the customer Transactions tab show "−" (U+2212) in front.
  - *Old documents keep the old migration number.* Specs and ledgers of finished units name the audit log migration as 2100000025; they are records and are not edited.
  - *Seed pick (spec §4.6).* Posted refund: from the seeded posted sales receipt 1004 (Harborview Hospitality Group, 2026-11-03), dated 2026-11-12, Check 20417, from 1000 Business Checking (the fixture's `REFUND_RECEIPT_IDS.posted`). Draft: `REFUND_RECEIPT_SEED_DRAFT_ID`. Payout: the fixture's payout row names the p2-credit-memo seed memo of Harborview, which the seed must not touch; so checkpoint 1 adds to the fixture a seed-only credit memo `REFUND_SEED_CREDIT_MEMO` (customer Aspen Ridge Dental, `cust_aspen_0001`, dated 2026-11-16, one taxable Item line, "Denver combined" tax, no invoice link) with `REFUND_SEED_CREDIT_MEMO_LINES`, and `REFUND_SEED_PAYOUT` with `REFUND_SEED_PAYOUT_LINES` (a payout of part of it, dated 2026-11-17, Bank transfer, from 1000 Business Checking).
