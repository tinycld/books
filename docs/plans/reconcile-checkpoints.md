**Rules for the code**

- Row types come from the query result (`type Row = NonNullable<typeof rows>[number]`); no hand-written row interface. Pure helpers take `Pick<…>` of the generated types `BooksReconciliations`, `BooksReconciliationLines`, `BooksReconcileLines`.
- Reads are `useLiveQuery` with `{ query, queryKey }`; a load error is detected on its query and Retry calls `recoverLiveQueries` once over every failed query through `mergeRecoveries` (`lib/live-recovery.ts`). In e2e a load error is made with `route.fulfill({ status: 400 })` (pbtsdb reports an error only for a 4xx), and the route is removed with `page.unrouteAll({ behavior: 'wait' })` before Retry.
- Writes are `useMutation` from `@tinycld/core/lib/mutations` with pbtsdb `insert` / `update` / `delete`. A screen that must stay through a write sets a synchronous Zustand flag before the mutation starts and clears it in `onSettled`.
- Forms are `useForm` + `zodResolver` from `@tinycld/core/ui/form`; server errors through `handleMutationErrorsWithForm`. No `useState` for an error text.
- Keys: the screen takes the `list` scope with `useShortcutScope('list')` (`tinycld/core/lib/shortcuts/scopes.ts`) and its keys register with `useRegisterShortcuts` (`tinycld/core/lib/shortcuts/use-register.ts`); a button with a key is a core `ShortcutButton` with `scopeOwner`. An open `Dialog` or `ConfirmDialog` pushes its own scope, so no list key fires under it. The pattern to copy is `hooks/useReviewShortcuts.ts` with `lib/review-shortcuts.ts`: a pure key map, state and handlers read through refs at press time, keys registered only while offered, `releaseDomFocus` before a movement key.
- A server refusal text is written without its final period where PocketBase adds one (read `refuse`, `refuseNamed`, `refuseField` in `server/errors.go` first). E2E asserts the text the screen shows.
- Light and dark: semantic classes and `useThemeColor` only. JSX stays small: state, handlers and derived values are in the hooks named in each checkpoint.
- Logging: `log.warn('books.reconcile', …)` on the client; `logging.ForPackage("books")` on the server.
- Test ids, widths, row heights, word tables and texts are those of the scratch route `tinycld/books/screens/helix-mockup.tsx`. Its helpers `totalsOf`, `matchesFilters`, `statusOf` and its word tables move into `lib/reconcile.ts`; no built file imports the scratch route.

**Spec:**
- "A **reconciliation** is one comparison of an account with one bank statement: an account, a statement ending date and a statement ending balance."
- "A Books transaction here is one posted journal line on the account. It is **cleared** when the user has marked it as on the statement in a reconciliation that is in progress, and **reconciled** when that reconciliation is finished."
- "**Beginning balance**: the statement ending balance of the account's last finished reconciliation; $0.00 when the account has none (the opening balance entry is then a transaction to clear)."
- "**Cleared balance**: the beginning balance plus the cleared transactions that raise the account's balance, less those that lower it."
- "**Difference**: the statement ending balance less the cleared balance. A reconciliation can be finished only at a difference of $0.00."
- "Accounts of type `bank` with any detail type (Checking, Savings, Money market, Cash on hand, Trust account), and accounts of type `credit_card`. The detail type changes nothing on the screens. A bank connection is not necessary."
- "A reconciliation starts only on an active account. An account that becomes inactive keeps its reconciliation in progress: the accounts screen does not list the account, and the register's Reconcile button still opens the reconciliation, which can be finished or discarded." (the server part here: create refuses an inactive account, update and delete do not read `inactive`; the accounts screen is checkpoint 2, the register button checkpoint 5)
- "An account has at most one reconciliation in progress."
- "Voiding or editing a transaction (an edit voids the original and posts a correction) that is cleared in a reconciliation in progress removes its cleared mark in the same server transaction. The correction is then a transaction to clear."
- "Voiding or editing a transaction that is reconciled is refused: "Expense 12 is reconciled on 1000 Business Checking (statement of Oct 31, 2026). It cannot be voided or changed." The same refusal serves every document screen, because each voids through the journal entry."
- "A posted transaction dated on or before a finished statement date can still be posted later (a late entry). It is then a transaction to clear in the next reconciliation, and it does not change a finished one."
- Spec §4 "Schema", "Server", "Fixture and seed" in full, with the settled differences 1 and 2.

   ```sql
   SELECT l.id AS id, l.id AS line, l.account AS account, l.entry AS entry, l.date AS date,
          l.debit AS debit, l.credit AS credit,
          (CASE WHEN l.memo != '' THEN l.memo ELSE e.memo END) AS memo,
          e.number AS number, e.doc_type AS doc_type, e.origin AS origin, e.document AS document,
          COALESCE(c.display_name, v.display_name, '') AS payee,
          COALESCE(rl.reconciliation, '') AS reconciliation,
          COALESCE(rl.finished, FALSE) AS finished,
          EXISTS (SELECT 1 FROM books_bank_match_lines m WHERE m.line = l.id) AS bank_matched
   FROM books_journal_lines l
   JOIN books_accounts a ON a.id = l.account AND a.type IN ('bank', 'credit_card')
   JOIN books_journal_entries e ON e.id = l.entry AND e.status = 'posted' AND e.origin != 'void_reversal'
   LEFT JOIN books_customers c ON c.id = l.customer
   LEFT JOIN books_vendors v ON v.id = l.vendor
   LEFT JOIN books_reconciliation_lines rl ON rl.line = l.id
   WHERE l.posted = TRUE
   ```
