## Decisions that apply to every checkpoint

Plan decisions:

When a Go spec test of checkpoint 1 finds that the engine refuses a spec or gives a wrong figure, the agent stops and reports it (`STOPPED: core report engine: <the refusal>`); the fix is a core checkpoint 0 that the driver plans. No agent designs around it and no agent edits core.

5. **Server-set fields.** `number`, `sequence`, `balance`, `currency`, `sent_at`, `sent_to` are never sent by a client. A new record that holds a value in one of them is refused in the model create hook, inside `serialized`, with `refuseServerFields` (`server/entries.go:329`: "Books sets these fields itself: number."). The check is the pattern of `checkNewSalesDoc` (`server/sales_documents.go:473`: a field is set when its string value is not the empty value of its type; an empty number field reads "0"), with the statement's own field list in `server/statements.go`. The hook then sets `number`, `sequence`, `balance` and `currency`. The collection has no update rule; only the send route updates a row (`app.Save`).
6. **The builder runs as the reader.** `documentKind.Build` (`server/pdf_kinds.go`) has no reader. `documentKind` gains `BuildAs func(ctx context.Context, app core.App, auth *core.Record, record *core.Record) (pdfDocument, error)`; `writePDF` (`server/pdf_routes.go`) calls it with `re.Auth` when it is set, else `Build`. Only the `statement` kind sets it. The public estimate route never reaches a kind with `BuildAs`.
7. **One statement value, three readers.** `statementData` (Go, `server/pdf_statement.go`) is built once from one report run. The PDF (`statementPDFDocument(data)`), the email (`statementEmail(data, business)`) and the file name (`statementFileName(data)`) read that one value. No reader runs the report a second time.
8. **Audit of a send.** Core audit hooks are bound to record requests (`tinycld/core/server/audit/audit.go` `bindCollection`), so the send route's `app.Save` writes no audit row by itself. `audit.Log` (`tinycld/core/server/audit/log.go:15`) writes `metadata` only, and the Books audit view reads the `changes` column, which only the unexported `logUpdate` (`tinycld/core/server/audit/audit.go:218`) fills. So the send route saves through the update-request hook chain, which the registered audit hook is bound to (`audit.go:117`): it loads the row, sets the sent fields, and calls `re.App.OnRecordUpdateRequest(statementsCollection).Trigger(&core.RecordRequestEvent{RequestEvent: re, Collection: …, Record: record}, func(e *core.RecordRequestEvent) error { return e.App.Save(e.Record) })` (read the event's fields in `tinycld/third_party/pocketbase/core/events.go` and how `apis/record_crud.go` builds it). The audit hook then writes the "updated" row with `changes` holding `sent_at`, `sent_to` (and `email` when it changed). Checkpoint 2's Go test asserts the `changes` column. When the trigger cannot give that row, the agent stops: `STOPPED: core audit: no exported update logger` (a core checkpoint 0); it does not fall back to `audit.Log`.
9. **Date rule: one case table for TypeScript and Go.** `server/testdata/statement_date_cases.json`, each case `{ "name", "type", "statementDate", "startDate", "endDate", "field" ("" when it is taken, else "statement_date" | "start_date" | "end_date"), "message" }`. **Spec:**
- "**Balance forward.** For one customer and a period (start day to end day): one line "Balance forward" with the customer's balance before the start day; then one line for each posted Accounts receivable line of the customer dated in the period, oldest first, with its date, its activity ("Invoice 1042", "Payment 317", "Credit memo 3", "Journal entry JE-12"), its amount (a charge positive, a payment or credit negative) and the running balance after it; then the **Amount due**: the balance on the end day. - "**Open items.** For one customer and the statement date: one line for each item of the customer that is open on that day (an invoice with an open amount, an unapplied payment, an unapplied rest of a credit memo, a manual journal line), in due-date order, with its date, its activity, its due date and its open amount (a credit negative); then the **Amount due** (the sum) and an aging line: Current, 1 - 30, 31 - 60, 61 - 90, 91 and over. The amount due equals the customer's Total on the A/R Aging report for the statement date."
- "A statement covers one customer row. A sub-customer gets its own statement; a parent's statement holds the parent's own lines only (Q8)."
- "**Statement number** (human, 2026-11-20; replaces "no statement number" of Q11). Every saved statement has a number from its own Books number sequence, document type `statement`: prefix "ST-", first number 1001, so the first statement is "ST-1001" and no statement shares a number with an invoice. The server gives the number when the statement is stored (as an estimate takes its number at its first save); a refused store takes no number. The numbers of one run are in the order the server stores the rows, which is not the order of the list.
