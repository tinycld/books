## Decisions that apply to every checkpoint

- **A payment is its own screen, not a sales-document kind** (spec §2 Q1: not a forms host; no lines, no tax, no PDF). Go: `server/payments.go` (guards), `server/payment_posting.go` (post, void, correction), `server/invoice_balance.go` (every write to `books_invoices.balance`). Client: `components/payments/`, `hooks/usePayment*.ts`, `lib/payment-*.ts`, `stores/payment-save-store.ts`, routes `screens/payments/new.tsx` and `screens/payments/[id].tsx`.
- **Shared document chrome (checkpoint 2).** `DocumentHeader`, `DocumentActionBar` and `DocumentMoreMenu` read only `testId`, `shortcutGroup`, `figure`, `helpTopic` and `lifecycle` of the kind. Checkpoint 2 adds `components/documents/document-chrome.ts`: `type DocumentChrome = Pick<SalesDocumentKind, 'testId' | 'shortcutGroup' | 'figure' | 'helpTopic' | 'lifecycle'>`, `DocumentChromeContext = createContext<DocumentChrome | null>(null)`, and `useDocumentChrome(): DocumentChrome` (the chrome context's value; else the kind context's `doc`; else it throws, lesson 33). The three components switch from `useDocumentKind().doc` to `useDocumentChrome()`; every invoice, receipt, estimate, bill and expense test id stays the same. `lib/payment-kind.ts` exports `PAYMENT_CHROME: DocumentChrome = { testId: 'payment', shortcutGroup: 'Receive payment', figure: { label: 'Amount received', testId: 'figure' }, helpTopic: 'books:receive-payment', lifecycle: 'posting' }`, and the payment screen provides it.
- **Form values** (`lib/payment-values.ts`, checkpoint 2): `type PaymentEntry = { amount: string; open: number; number: string }` (a row's typed payment, its open balance and its invoice number, so the schema checks a row without reading the list); `type PaymentFormValues = { customer: string; date: string; payment_method: PaymentMethodKey | ''; reference_no: string; deposit_to: string; amount: string; amountTyped: boolean; payments: Record<string, PaymentEntry>; memo: string }`, `payments` keyed by invoice id (a row with no entry is at zero; entries at zero are removed, so they are never stored). Field names are the server's, so a server refusal keyed `customer`, `date`, `deposit_to`, `reference_no` or `amount` lands under its field with no mapping. `amountTyped` is form state the user changes by typing in Amount received (spec §3.4); it is not validated. It is not stored, so a reopened draft or a correction derives it (plan decision): `amountTyped` is true only when the stored amount differs from the stored applications' sum (the user typed an amount that left a credit); otherwise it is false and Amount received follows the rows again.
- **Amount received input.** Books `MoneyInput` is typed to the opening-balances form, so Amount received and each row's Payment are core `TextInput`s (`keyboardType="decimal-pad"`, right-aligned, `tabular-nums`, `useSelectAllOnFocus`) under a `Controller`, in `components/payments/PaymentMoneyField.tsx`. - **Deposit to options** (`lib/payment-deposit.ts`, checkpoint 2). `depositAccountOptions` lists active accounts only and `defaultDepositAccount` falls back to the first bank account, so the payment wraps them: `paymentDepositOptions(accounts, storedId): { options; triggerLabel }` puts `{ value: '', label: 'Undeposited funds (created when you post)' }` first when no active Undeposited funds account exists (`accounts` rows with subtype `undeposited_funds`, the subtype `ensureUndepositedFunds` writes), then `depositAccountOptions(accounts, storedId)`; `paymentDefaultDeposit(accounts): string` is the first active Undeposited funds account, else `''`. A chart with no bank and no Undeposited funds account lists only the `''` option. The field is core `SelectInput` with `placeholder={triggerLabel}` and the stored id kept from mount (`useState(() => …)`), as `DepositAccountField` (`forms/payment-fields.tsx:186`) does, so a stored inactive account shows by name for the value it mounted with.
- **Customer field.** `PaymentCustomerField` is Books `SearchPicker` over `useDocumentCustomerOptions(term, isOpen)` with its `isLoading`, `loadFailed` and `onRetry` passed through; the trigger label of a stored customer comes from `useRecord` of `books_customers` (so an inactive stored customer shows by name).
- **Allocation is pure** (`lib/payment-allocation.ts`, checkpoint 2): `type OutstandingRow = { id: string; number: string; date: string; due_date: string; total: number; open: number }` (rows in list order: oldest due date first, then number). Functions (all in integer cents through `moneyInputCents` / `centsToText`, never dollars): `entryCents(entry: PaymentEntry | undefined, currency: string): number` (0 for missing or unparsable), `amountToApply(payments, currency): number`, `amountToCredit(amountCents: number | null, applyCents: number): number` (0 when not above zero), `tickRow(payments, row): payments`, `untickRow(payments, rowId): payments`, `typeRowPayment(payments, row, text): payments` (removes the entry at zero), `toggleRow(payments, row, currency): payments` (⌥↵: empty or zero takes `row.open`, else removes), `spreadAmount(rows, amountCents): payments` (oldest due first, each up to its open balance), `payAll(rows): payments`, `clearPayments(): payments`, `followedAmount(payments, currency): string` (the Amount received text while not typed: Amount to apply, `''` at zero).

- **Where the sum rule runs (plan decision).** Spec §4.3 lists `sum ≤ amount` among the guards. A draft save writes the header and its applications as separate records, so a sum check on each write would refuse an honest edit that lowers the amount before it lowers a row. The server therefore checks each application on its own write (posted invoice of the payment's customer, once, amount > 0, at most 500 per payment) and checks `sum ≤ amount` and each row against the invoice's balance at posting, inside the posting transaction; the client's zod schema checks the sum on every Save draft and Post.
- **Write order of a save** (checkpoint 2): (1) remove the stored applications the form no longer holds, (2) insert or update the `books_payments` row, (3) update and insert applications in list order (`position` = place among the stored rows from 0), (4) for Post, update `status: 'posted'`. The unique (`payment`, `invoice`) index never meets a duplicate because removes run first.
