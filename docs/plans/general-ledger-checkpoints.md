## Plan decisions (where the plan departs from the spec's letter, and why)

- **P1 — Q1 migration.** Spec §5 says the `customer`/`vendor` relations are "edited into migration `2100000002`". That migration runs before `2100000003_create_books_customers.js` and `2100000004_create_books_vendors.js`, so a relation there cannot name either collection. The fields go in a **new** migration `pb-migrations/2100000009_add_books_journal_line_parties.js` (unreleased package, version 0.1.0; a new file also applies to dev databases that already ran 02–08).
- **P2 — e2e count.** A screen adds at most 12 e2e runs; spec §7 lists 14 runs for the report. The plan keeps every behavior and uses 9 runs: item 3 (normal side) and item 6 (All dates) fold into item 2 (one goal: read an account's balances across periods); item 10a at 1280 folds into item 1 (opening the report shows every column); item 10 (phone layout) is the phone run of item 1; item 5's phone run is dropped because Rows and Accounts on a phone run core's chip row and `SourceChoicePicker` sheet only, which core's `tests/e2e/reports-source-params.spec.ts` drives at phone size. Item 11 (journal entry Name, desktop and phone) is the entry screen's, 2 runs.
- **P3 — Trial Balance version.** Checkpoint 0 makes `reports.CurrentVersion` 3. `reports.Load` upgrades every older spec to the current version (`core/server/reports/spec.go:362-371` sets `doc["version"] = at + 1`; `UpgradedFrom` stays 0 for an identity step), so `TestTrialBalanceSpecLoads` (`server/report_trial_balance_test.go:276`, "version 2 with no upgrade") fails as soon as the core PR merges, whatever the Trial Balance spec writes. Spec §11 holds either way: `ReconcileShipped` re-stores a shipped spec only when its `Revision` rises, and the Trial Balance stays revision 1. So the Trial Balance spec keeps `Version: reports.CurrentVersion`, and the test's assertion becomes "version `reports.CurrentVersion`, `UpgradedFrom` 0". That one-line test change lands **in checkpoint 0**, on the books branch, right after the core merge (Do step 4), so the books branch is never red against merged core; checkpoint 1 commits it.
- **P4 — reversals and replacements keep the party.** `server/reversal.go` copies a line's account, amounts, memo and position into the reversal (`writeReversalLines`, reversal.go:123-134); it also copies `customer` and `vendor` (the fixture's void pair shows the Name on both entries). The line party guard skips lines of an entry whose `reverses` is set (Books writes those lines; an inactive party must not block a void). Edit of a posted entry makes a replacement draft (`replaces` set) with **new** lines; a new line there may keep a now-inactive party when a line of the replaced entry names the same party (the user did not choose it again; refusing would block every correction of an old entry). A party the user changes to must be active.
- **P5 — long seeded section.** `GENERAL_LEDGER_LONG_SECTION` is seeded as **two** posted journal entries of 131 lines each (130 debit lines of 1.00 to Business Savings and one credit of 130.00 to Business Checking), dated `${year}-09-15` and `${year}-09-16`: Business Savings gets 260 lines in one section, the checking register only 2, and each entry stays under the entry form's 200-line limit (`lib/entry-lines.ts:3` `maxLines`; `lib/entry-schema.ts:83`), so a user can still Edit either one.
- **P6 — e2e days.** `GL_DAY_1 = '2026-08-04'` and `GL_DAY_2 = '2026-08-18'` (exported from `tests/e2e/books-report-helpers.ts`): after the e2e close date and in no other spec's assertions.
- **P7 — refusal texts the spec does not word.** `msgLineBothParties = "A line can name a customer or a vendor, not both."`; `msgLinePartyInactive = "%s is inactive. Choose an active customer or vendor."`; `msgPartyOnLines = "%s is on journal lines. Make it inactive instead."` (spec §3 wording, `%s` the display name). `lib/entry-messages.ts` copies the three (`LINE_BOTH_PARTIES`, `LINE_PARTY_INACTIVE`, `PARTY_ON_LINES`), `tests/entry-messages.test.ts` fails on drift, and the entry schema's not-both issue uses `LINE_BOTH_PARTIES`.
- **P8 — core-owned behavior.** Customize, the loading/error/timeout/no-access states, Copy link, Save as, and the empty state's text with its "Show this fiscal year" / "Clear filters" actions are core's view, driven by core e2e (`reports-view.spec.ts`, `reports-failure-states.spec.ts`, `reports-share.spec.ts`). Books pins what Books owns: its spec (Go tests, including `TestGeneralLedgerEmpty`: an empty run returns only the Total row and the resolved period the empty text prints), its share (the Trial Balance's `report_shares.go`, unchanged), and the "Clear filters" path on a filtered empty run (e2e 4). An unfiltered empty General Ledger cannot be reached in the shared e2e book (seeded balances give every period opening rows), so "Show this fiscal year" stays with core's e2e. Section folding and Expand all / Collapse all are core's toolbar, but Books asserts them once (e2e 2), because the spec opens every section (`groups[].open`).
- **P9 — Name and the keyboard.** Name is optional, so it is not in the line's Enter walk (`lib/line-focus.ts` `LineColumn` stays `account | debit | credit | memo`); Tab reaches it in DOM order between Account and Debit.
- **P10 — zero side blank.** Core does not blank a zero money cell (`core/reports/lib/format.ts`), so the spec's `debit = [debit]` would print 0.00 on the zero side. The `debit` and `credit` columns use the formula `if(eq([debit], 0), null, [debit])` (detail rows) with `rollup: sum([debit])` (F6) on group, subtotal and total rows; the same for credit.
