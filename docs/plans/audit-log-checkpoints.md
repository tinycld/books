## Plan decisions (where the plan departs from the spec's letter, and why)

- **P1 — Go audit rows.** Spec §6 asks the Go `Run` test for "audit rows made by real request writes". A Books Go test can make one REST call per app (`apiReq` in `server/env_test.go`: a second `ApiScenario` on one app panics). So `server/report_audit_log_test.go` saves `audit_logs` rows the way core's hooks write them (the helper `mkAuditRow`, shaped from core `core/server/audit/audit.go` `newAuditRecord` / `ComputeDiff` / `BuildSnapshot`) over real Books records saved with `app.Save`, and **one** `apiReq` test proves the hook path end to end (a bookkeeper's PATCH of a product writes a row the view lists as `changed` with the bookkeeper's name). The e2e makes every event through the UI.
- **P2 — no seed wiring.** The view's rows come from core's audit hooks over real writes; seeding `audit_logs` would be a raw write of core's table, and the seed's own REST writes already log rows. The fixture (static run results and view rows for the reference) is typed against the generated `BooksAuditLog` in checkpoint 1 and is not imported by `seed.ts`.
- **P3 — journal entries.** Spec §3 "Entry points" names `EntryActionBar.tsx` for journal entries. That bar is the draft form's bar; a posted or void journal entry shows `EntryReadOnlyActions.tsx` (`EntryReadOnlyView.tsx`). Both get Audit history (the draft form only for a saved draft). Transfers share both bars but are not in the spec's list, so `TransferReadView` and `TransferForm` pass no history handler and keep their bars (`tests/e2e/transfer-actions.spec.ts` line 231 asserts no `entry-more` on a void transfer).
- **P4 — display.** Phase 3 pass 2 measured the display: `oneLine.minWidth` 760px and no least width for User and Record type. Spec §5's `display` bullet now says so (edited in phase 4). The Go `display` equals the fixture's `AUDIT_LOG_DISPLAY`.
- **P5 — collaborator level.** `tests/e2e/books-settings.spec.ts` moves the collaborator through every Books level on the shared e2e DB. A test that signs in as the collaborator while another worker sets them to None would fail at random. So checkpoint 4 adds a one-worker Playwright project `books-access-level` (grep `/\(collaborator level\)/`), puts in it the six `books-settings.spec.ts` tests that change the collaborator's level or sign in as the collaborator (their titles gain " (collaborator level)"): "Access: owner row is locked and search filters the list" (line 492), "Access: the owner changes the collaborator through the levels" (518), "Access: a slow list refresh still shows the saved level after leaving and re-entering" (543), "Access: a bookkeeper reader sees read-only Settings" (571), "a read-only member sees 1099s without edit controls" (839) and "can preview the sample invoice" (882), plus the new access test; the `books` project inverts that grep and depends on it, as `purchase-lines-setting` does. The spec's local `chooseLevel` and `levelOf` (lines 95–110) move to a new shared `tests/e2e/books-access-helpers.ts` (`setCollaboratorLevel`, `collaboratorLevel`), which `books-settings.spec.ts` then imports.
- **P9 — a line event's changes.** Spec §3 writes a changed line inline ("Line 2 — Changed: Amount 120.00 → 150.00"). A line change often moves several fields (account, amount, memo), so the plan draws a line event as its title "Line 2 — Changed" followed by the same Field | Before | After table as the record's own events. Every value rule is the same; only the inline arrow form is replaced.
- **P10 — the view's live sources.** Spec §5 says `RegisterView(… <the eight parent collections>)`. The view reads the eight **line** collections (to find a live line's parent), so those are its sources; a parent document's own write already reaches the view through `audit_logs`.
- **P11 — reads beside the one live query.** Spec §5 "Client" says `materialize()` per relation in a row component. A Field | Before | After value names a relation by id inside a JSON column, not by a relation field of the row, so `materialize()` cannot reach it; `FieldValue` reads it with `useRecord`, and the header reads the live record with its own query. Each read's loading and error state is named in checkpoint 2 Do 4–5.
- **P12 — Go and fixture copies.** The Go code is the source of the spec (`auditLogShipped()`), the event options, the record type options and the display. `TestAuditLogSpecLoads` compares them with a golden file `server/testdata/audit_log_spec.json`, and a vitest `tests/audit-log-fixture.test.ts` compares the fixture's `AUDIT_LOG_DISPLAY`, `AUDIT_EVENT_OPTIONS`, `AUDIT_RECORD_TYPE_OPTIONS`, `AUDIT_LOG_TITLE` and `AUDIT_LOG_DESCRIPTION` with the same file, so a drift in either copy fails a test.
- **P13 — no-access hub and report link.** A user at Books level None has no viewer share (Go: `report_shares_test.go`) and core answers "no access" on the report link (core `reports-share.spec.ts`). No Books e2e drives it; checkpoint 4's e2e drives the Books-owned history no-access state.
- **P14 — Show 50 more.** The window is pinned by the hook test (`tests/use-record-history.test.tsx`, 51 rows); `RecordHistory` shows `history-show-more` only when `hasMore` is true and calls `showMore` on press. No e2e makes 51 events.
- **P6 — core-owned behavior.** Loading, error and Retry, timeout, no access, empty and its actions, Customize, the heading sort and Reset, paging by 200 and the phone row layout engine are core's report view, driven by core e2e (`reports-view.spec.ts`, `reports-failure-states.spec.ts`, `reports-share.spec.ts`, `reports-paged-groups.spec.ts`, `reports-wrap.spec.ts`). Books pins what Books owns: the view, source and spec (Go), the share (`server/report_shares.go`, unchanged), the events and labels, the display, the history screen and panel, the More items. Gate 2 compares `report-loading-*` and `report-error-*` nowhere: they are core's view over a static model.
- **P7 — test files.** Spec §6 names three e2e files; the plan uses the five above, so each checkpoint's tests sit in a file of their own and a checkpoint's test writer never edits another checkpoint's file.
- **P8 — the More item has no key.** The read views register a key for each button and each More row (`useMoreKeys` in `DocumentReadActions.tsx`). Audit history only opens a screen and is a menu row, not an action button, so it registers no key (the data-entry shortcut rule covers action buttons). It is drawn from its own prop, not from `DocumentReadItem`, so `useMoreKeys` never sees it.

**Sizing:** 4 checkpoints after checkpoint 0 (the view and the report; the record history screen; the history panel; the More items and help). The panel is its own checkpoint because it is the one part that rides on core D5 end to end; a reviewer can accept the screen and reject the panel.
