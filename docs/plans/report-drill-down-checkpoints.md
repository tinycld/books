## Plan decisions (where the plan departs from the spec's letter, and why)

- **D1 — e2e count.** Spec §7 lists 18 e2e tests (10 + 7 + 1); a screen adds at most 12 (checkpoints.md). The plan keeps 12 and moves the rest into one test of the same goal or into core's e2e, where the behavior is core's view code over any report:
  - Screen spec (9): §7 items 1, 2 (with item 8 folded in: the drill of item 2 is reached by Tab and Enter), 3, 4, 5, 6, 7, 9, 10.
  - Panel spec (2): §7 panel item 1 with item 2 folded in (one goal: read figures in the panel; the second press replaces the first), and item 7.
  - Phone spec (1): §7 phone item 1.
  - Panel items 3 (scoped params), 4 (Open as full report and its back link), 5 (✕, Escape, Customize closes the panel and a figure press closes Customize), 6 (crossing the width with no rerun) are core's view code with no Books logic in them: checkpoint 0's core e2e `tests/e2e/reports-drill.spec.ts` drives each one on `salesstub` (its tests 3, 4 and 5). Books' own part of them (the Books report fitted in the 480 px panel, its figures and totals) is in panel test 10.
- **D2 — core-owned states.** Loading, error with Retry, timeout with Retry and no access of the panel and of the opened report are core's view (`ReportDrillPanel`'s own states and `ReportStates`), driven by core e2e (`reports-failure-states.spec.ts`; `reports-drill.spec.ts` test 6 for a reader without the target). Gate 2 compares `panel-loading-*`, `panel-error-*`, `panel-no-access-*`, `screen-loading-*`, `screen-error-*`, `screen-timeout-*` and `screen-no-access-*` nowhere: they were captured in phase 3 from a static model only. The empty state's text and action are core's (`emptyMessage`, `emptyAction` in `core/reports/lib/params.ts`: an optional param with a value gives "Clear filters", else "Show this fiscal year"); Books pins that `accounts` has no default (so it is optional) and that a run with no line gives no section and a blank Total (Go), and gate 2 compares `screen-empty-*` and `panel-empty-*`.
- **D3 — widths are measured on the shipping route.** Phase 3 measured Transaction Detail inside the Books shell: a 956 px row (1280 window with the Books sidebar) did not fit one line, so the fixture has `oneLine` 960px. The shipping route `/a/reports/<id>` has no package sidebar. Checkpoint 1 ships `oneLine.minWidth` "960px" and measures it again there with `waitForTableFit` at 1280 and 1024 (checkpoint 3: the 480 px panel, 390 and 375): it keeps 960px when the one-line row at 1280 shows Date, No. and Amount uncut, and raises the width to the narrowest row where they are uncut otherwise; the measured layout names and the final width go into the ledger. E2E asserts the spec's geometry (headings and every Amount inside the table's right edge, no sideways scroll), never a layout name.
- **D4 — the fixture's drill types.** The fixture's local `DrillTarget` / `DrillParams` are replaced by core's D1 types in checkpoint 0's books-side step (Do step 5), together with the re-capture of `statement-*` and `panel-*` (spark 1 needs core's drilled `RowCell`); the fixture and the re-captured shots are committed with checkpoint 1.
- **D5 — the entry route table.** `server/entry_routes.json` is the one table (spec §5). Go embeds it (`//go:embed`, as `server/entry_type_labels.go` embeds `entry_type_labels.json`; embed cannot reach outside `server/`), and `tinycld/books/lib/entry-route.ts` imports it by relative path (`../../../server/entry_routes.json`; `resolveJsonModule` is on in core's `tsconfig.package-base.json`). The web export of every e2e run proves Metro resolves it; native is not executed.
- **D6 — the Trial Balance's as-of day in e2e.** The Trial Balance opens at End of last month; a line posted today is not in it. §7 item 5 sets As of to Today (`chooseAsOf(page, { preset: 'today' })`) before it reads B's figure.
- **D8 — the Accounts chip.** Spec §3 says both chips always show "so the reader sees what the drill chose". Every drill sets `accounts`, so core's control row (`controlItems` in `core/reports/lib/params.ts`: an optional param is a chip once set) shows it as a chip on every drilled report and in every panel; e2e tests 5–10 and 12 assert `report-param-accounts`. Opened from the hub with no account chosen, `accounts` (optional, the Trial Balance's param, no default) is under Add filter, as on the Trial Balance and the General Ledger; a default would filter the hub report to some accounts, which the spec forbids ("With no account chosen, the report lists the lines of every account"). Checkpoint 1 test 4 asserts the Add filter entry `report-add-filter-accounts` on the hub-opened report.
- **D9 — generic report behavior on Transaction Detail.** Paging (F7), and Customize (Divide by 1000, Without cents, Negative numbers, red negatives, column show/hide) are core's view over any report, pinned by core's `reports-view.spec.ts`, `reports-paged-groups.spec.ts` and `reports-scroll-anchor.spec.ts`. Books pins what is its own: Date is the label column (core never offers the label column in Customize; `TestTransactionDetailSpecLoads` pins `Detail.Label` `[date]`), and checkpoint 1 test 4 sorts by Amount once on the full report.
- **D7 — opened lines of the P&L and the Trial Balance.** Spec §3 D2 names them among the rows that open. Their `detail.open` ships in checkpoint 1 with the General Ledger's and the Journal's (one `entryOpenPath()`, one revision bump per report); the Go tests pin `open` on each report's detail rows, and e2e test 2 presses a General Ledger line and a Journal line (core's row press is the same code on every report).
