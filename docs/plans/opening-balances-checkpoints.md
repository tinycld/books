## Decisions that apply to every checkpoint

- **Money (one place):** amounts are integer cents in memory and in storage. PocketBase stores them as float64, exact only up to 2^53-1 (`maxStoredAmount` in `lib/money.ts` and in `server/posting.go`). Text becomes cents only through `parseMoney` (`lib/money.ts`), which returns `null` above `maxStoredAmount`. Cents become text only through `formatMoney` or `centsToText`. No screen, hook or component does arithmetic on dollars; all sums go through `lib/opening-balances.ts`, which guards overflow and rounds nothing because its inputs are already whole cents. Two different limits exist and are told apart: text above `maxStoredAmount` cannot be parsed, so the field shows the error `Amount is too large` (`amountError`); a parsed line above `maxLineAmount` (10^15 cents, the server's `maxAmount`, which is below `maxStoredAmount`), or a sum above `maxStoredAmount`, is `problem: 'too-large'` and the totals strip shows "Too large".
- **Sign convention:** an amount typed for an account is in the account's natural sign: a positive asset is a debit balance, a positive liability or equity amount is a credit balance, and a negative amount is the opposite side. The side comes from `accountTypeDef(type).normal` in `lib/account-types.ts`.
- **Negative amounts on every keyboard:** the iOS and Android decimal pads have no minus key. `MoneyInput` therefore uses `inputMode="decimal"` and ships a 44pt sign toggle button (`opening-sign-<accountId>`, label "Switch sign") that adds or removes a leading `-`. A hardware or web keyboard can still type `-250` directly.
- **Dates are ISO strings** (`YYYY-MM-DD`). No `Date` arithmetic outside `lib/register-range.ts`. Tests pass `today` in; no test reads the clock. A partial or invalid date text never reaches `formatDay` (which would print "Invalid Date"): `dayLabel(day)` in `lib/opening-balances.ts` returns `''` unless `isRealDay(day)`.
- **Every Go guard that reads entry or account state before a write runs inside `serialized`** (`server/ledger.go`), because PocketBase runs record create and update without a transaction.
- **Form lifecycle (one place):** the screen hook decides `state`; `OpeningBalancesScreenView` mounts a child `OpeningFormScreen` only when state is `new`, `draft` or `replace` and the user can write, and gives it `key={formKey}` where `formKey` is `'form'` for those three states. `useOpeningBalancesForm` runs inside that child, so its defaults (the fiscal-year date, the draft's lines) are computed from loaded data on the first render; there is no effect and no re-seed. A save that turns `new` into `draft` does not change the key, so the non-atomic entry-then-lines write never re-seeds the form from half-written lines. Another session's later edit to the same draft is not merged into an open form. After a successful save the form calls `form.reset(form.getValues())` so `isDirty` is false. Screen `isReady` includes the lines query when an entry exists (a superset of the spec's "accounts, settings and the opening-entry query").
- **Validation mode and error rendering:** `useForm({ mode: 'onChange' })`. The core `TextInput`/`SelectInput` render the date and memo errors under their fields; `MoneyInput` renders its own error text (`opening-amount-error-<accountId>`) under the input; `FormErrorSummary` (test id `opening-error-summary`) shows root and server messages and is given the form errors without the `amounts` key, so an amount error is not printed twice.
- **Layout regions:** header (fixed) / body (the only scroll area: date block, grid, and on a phone the preview disclosure) / footer (fixed: the totals strip, then the action bar). The totals strip and the action bar are outside the scroll area at every width.
- **Capture for gate 2** (one definition; each checkpoint names its states and manifest). From the package: `E2E_PORT=7220 E2E_PORT_2=7221 HELIX_CAPTURE=/Users/nas/tmp/tinycld/books-reports/books/docs/plans/opening-balances-evidence/cp<N>/capture.json pnpm exec tinycld-pkg test:e2e -- -g helix`. That manifest has `outDir: "."` and covers states reachable on a fresh DB without typing (`blank`, url `/a/books/opening-balances`, `ready: "opening-balances-screen"`). A state that needs typed data, a forced response or a posted entry is captured by the scratch spec `tests/e2e/helix-states.spec.ts` (git-excluded with `.git/info/exclude`, deleted by `finish.mjs`, describe title `helix-states`, selected by the same `-g helix`): it logs in, drives the UI to the state, and writes `<state>-<width>-<scheme>.png` into the same `docs/plans/opening-balances-evidence/cp<N>/` folder. Each `e2e` invocation starts a fresh DB, so a state that needs a posted entry is built inside that one spec.
- **E2E rules:** all e2e for this feature live in ONE file, `tests/e2e/opening-balances.spec.ts`, because the feature has one entry per database and the suite runs two workers across files; tests inside one file run in file order in one worker. **Each run starts from a fresh seeded DB** (`pnpm run e2e:serve` clears the data dir and `playwright-global-setup.ts` seeds it); the suite does not claim to be re-runnable against a stack that already holds an opening entry. File order is the contract: the describes run in checkpoint order (states, grid, preview, draft, post, replace); a test that needs the form runs before the post test; a test that needs a posted entry runs after it. The Post test posts once (at the desktop size) and checks the posted view at the desktop size and again after `page.setViewportSize` to the phone size, because a second post would turn into a replacement. Every other flow that writes ends by discarding its draft and runs at both sizes. Amounts are entered only on Office Equipment and Company Card (accounts no other Books spec opens); a posted opening entry is permanent for the run and moves their balances, which the other specs do not read. Every test that needs a form passes through `openOpeningBalances(page)`, defined once in `tests/e2e/opening-balances-helpers.ts` (created in checkpoint 2) with `DESKTOP`, `PHONE`, `isPhone` re-exported from `account-register-helpers.ts`. Reads may be mocked with `route.fulfill`/`route.fetch` (loading, empty chart, read-only level, forced 400 refusals); data is never written with raw PocketBase calls. The seed has no read-only Books member: the read-only layout is reached by fetching the real `books_access` response and fulfilling it with `level: 'read_only'`, `can_write: false`; this covers the client layout only, and server enforcement stays covered by the Go tests. Level `none` has no e2e (no seeded user); `openingScreenState` covers it.

   // checkOpeningEntry refuses a second live opening entry. The entry being
   // replaced is the one allowed exception: it is posted, and posting the
   // replacement voids it in the same transaction.
   func checkOpeningEntry(app core.App, entry *core.Record) error {
       if entry.GetString("origin") != originOpeningBalance {
           return nil
       }
       others, err := app.FindRecordsByFilter("books_journal_entries",
           "origin = 'opening_balance' && status != 'void' && id != {:self} && id != {:replaces}",
           "", 1, 0, dbx.Params{"self": entry.Id, "replaces": entry.GetString("replaces")})

           return fmt.Errorf("books: read opening entries: %w", err)
       }
       if len(others) == 0 {
           return nil
       }
       return refuse("Opening balances are already entered (%s). Edit that entry.", entryName(others[0]))
   }
