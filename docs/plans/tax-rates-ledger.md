- **finding:** reviewer A, checkpoint 3, BLOCK 1: "'Make active' goes around the three new inactive refusals. (1) rates inactive, agency inactive, its account inactive, then agency active → an active agency with an inactive account; posting refuses an inactive account (posting.go:143), so the invoice unit will fail when it posts tax for this agency. (2) rates inactive, agency inactive, then one rate active → an active rate under an inactive agency; the default and customer pickers still list it. (3) group inactive, one of its rates inactive, then group active → an active group holding an inactive rate.   **rebutted because:** the spec and the plan chose this. Spec: "An edit dialog shows a stored account that has become inactive as the select's value and keeps it on save; the server checks the account only when it changes." and "the server checks only the rates added by the change"; Data: "a rate needs an agency that exists and is active when it changes". Checkpoint 2's tests, committed in d6fa0d0, require it: `TestTaxAgency_AccountChecks` "an agency whose account became inactive after it was saved can be renamed (make the agency inactive, then the account, then the agency active again with a new name: the account did not change, so it is not checked …)" and `TestTaxRate_KeepsAComponentThatBecameInactive` "make G inactive, then B inactive, then G active again (its components did not change, so B is not checked)". Changing it changes the approved spec, so it is the human's call (raised at the eval gate). The overclaiming comment at accounts.go:195 is fixed (F3).
