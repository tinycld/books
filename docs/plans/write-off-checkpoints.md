## Decisions that apply to every checkpoint

Plan decisions:
1. **Edit and Void on a written-off invoice (spec §3.4, Q9).** The invoice's bar does not change: a writer on a posted invoice keeps Edit (E) and Void (V), with or without a write-off, because `documentReadActions` offers both on every posted document and the spec keeps the refusal on the server. Void opens the shared void dialog; its confirm is refused by the server (`CheckVoid`) and the dialog shows "This invoice is written off. Void the write-off first." through `writeRefusalText` (`hooks/useDocumentReadActions.ts`, `voidDialog`), stays open, and the invoice stays posted. On a Sales list the row menu's Void is refused the same way; there the dialog closes and the text shows in the list's banner (the list's existing refusal path, `hooks/useDocumentRowActions.ts`). Edit opens the correction form (`router.replace` to the new-invoice route with `replaces`); its Post is refused by the server (`Replace`) and the text shows in the form's `FormErrorSummary`; the original stays posted. No client rule hides or disables Edit or Void. Create credit memo and Copy stay. With a balance of zero there is no Write off and no Receive payment (`writeOffOffered`, `receivePaymentOffered`).
2. **Bar order.** `documentReadActions` posted order becomes: apply, refund, pay, receive, edit, void, copy, credit, **write_off**, refundSale, refundCredit, entry, pdf. Row menu order (`documentRowMenuItems`): "Write off" directly after "Receive payment" (spec §3.1), which differs from the bar on purpose.
3. **One dialog host per screen.** `useWriteOffStore` holds `openFor: { invoiceId: string; owner: string } | null`. Each screen that can open the dialog mounts one `WriteOffDialog owner={owner}` (`owner` from `useId()`), and the dialog is open only when `openFor.owner` is its own. Without the owner, a list below an invoice read view in the stack would draw a second dialog.
4. **The dialog always reads its invoice by id** (`findOne`, `materialize()` of the customer), on the read view too: the row is in the store there, so no request goes out, and the figure is live on every screen.
5. **`written_off` is saved with `balance`.** Go sets `doc.Set("written_off", …)` and then calls `saveDocumentBalance`, which saves the whole record under `markBalancing`. `written_off` joins `balanceOnly`, `salesDocNewBooksFields` and `salesDocKeptBooksFields` (`server/sales_documents.go`), so a person's body cannot set it.
6. **Badge.** `ReadBalanceBadge` (`components/documents/document-kinds.ts`) already has a fourth argument, `refunded: ReadRefunded`; it gains a fifth, `writtenOff: number`, and `DocumentReadView`'s `readBadgeOf` passes the invoice's `written_off` from its `kindFields` (0 for every other kind). `writtenOffBadge(status, balance, total, writtenOff)` in `lib/document-lifecycle.ts` is pure: it answers `{ label: 'Written off', tone: 'muted' }` for a posted document with `balance <= 0` and `writtenOff > 0`, and `paidBadge(status, balance, total)` otherwise. `INVOICE_DOCUMENT.balanceBadge` is a wrapper `(status, balance, total, _refunded, writtenOff) => writtenOffBadge(status, balance, total, writtenOff)`, as `vendorCreditBadgeOf` in the same file wraps its badge.
7. **The write-off page is no document kind and no forms host.** It has its own screen, read view and bar; it gives `DocumentHeader` its texts through `DocumentChromeContext` (`testId: 'write-off'`, figure label "Amount written off", lifecycle `posting`), as the reference does.
8. **`TransactionKind` gains `write_off`**, but the Sales lists do not: `lib/sales-lists.ts` types `ALL_KINDS`, `NEW_ACTION_IDS` and `NEW_LABELS` by `SalesKind = Exclude<TransactionKind, 'write_off'>`; All sales and the kind tabs never run the write-off query. Only `customerTransactionsTab` adds the kind.
9. **The customer Transactions tab has no row menu today** (`components/party/page/PartyTransactionsList.tsx` draws none). To deliver spec §3.1 bullet 3 there, `PartyTransactionsList` gains an optional `rowMenu` prop and the customer tab passes a menu with the one row "Write off" on invoice rows where it is offered. The other Sales-list row actions are not added to the customer page (no spec asks for them). The vendor tab passes no `rowMenu` and does not change.
10. **Every e2e write-off goes to 6050 Bad debts.** The dialog's default account is the account of the newest posted write-off in the shared e2e database, so a spec that picked another account would change the default that a parallel spec asserts.
11. **Seed pick.** `WRITE_OFF_SEED`: customer Delta Freight Partners (`cust_delta_0001`), one posted invoice dated 2026-10-03 for $215.50 with no sales tax, written off whole on 2026-11-10 to 6050 Bad debts. The seed sets the fixture's record ids; the server assigns the numbers at posting, so a Gates line names the seeded pair by its customer, not by a number. No file under `tests/` names the customer today (`command grep -rl -E 'Delta Freight|cust_delta_0001' tests` gives nothing). Checkpoint 1 confirms the days against the report specs (its Do step 9) before it wires the seed.
12. **p5-ar-aging (Q17).** `ls pb-migrations/` on this branch shows no `books_receivable_lines` view. If a merge of main brings one before a gate, the checkpoint in progress adds `write_off` to that view so the write-off's Accounts receivable line belongs to its invoice, and names the edit in the ledger's Out-of-plan changes.
