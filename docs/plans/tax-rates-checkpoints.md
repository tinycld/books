## Decisions that apply to every checkpoint

- **Core (checkpoint 0), approved by the human on 2026-11-04.** The design gate recorded "core extension: none". Planning found two gaps, and the standing rule for the forms engine is "missing capability → implement it in core first" (memory `no-limits-reports-forms`): (1) a forms host cannot give a built-in the help text a seeded default form shows (core `hostLayoutSchema.fields` takes only `page` and `width`; core/server/forms `LayoutField` the same), and the spec's Taxable toggle has help text; (2) core `SelectInput` has no section headings, and the spec's default picker and Default sales tax field group rates "under their agency name". No core version bump and no `peerVersions` change (`'@tinycld/core': '>=0.8 <1'` stays), as with the earlier Books core changes: both fields are optional additions, Books is unreleased, and before the first Books release the release skill bumps core and pins Books' `peerVersions`.
- **Group components on the page (approved by the human on 2026-11-04).** `books_tax_rates.components` is a multi relation. TanStack DB correlates an includes subquery (`materialize`) only through an `eq()` of a parent field and a child field (`@tanstack/db` builder: "Includes subquery … must have a WHERE clause with an eq() condition"), so a group's component rows cannot be materialized by id list. The page therefore reads two live queries, as the spec says (agencies with their rates materialized; groups), and `buildTaxesView` looks a group's components up among the rates the agencies query already holds. That is the only cross-query lookup on the page; it is pure and unit-tested.
- **Order of a group's rates** (driver ruling on plan review A3): the groups card's second line lists a group's rates by rate name, caseless (`compareNames`), as the spec example "Colorado state 2.9% + Denver city 4.81%"; the seeded "Denver combined" line is "Colorado state 2.9% + Denver city 4.81% + RTD transit 1%". The group dialog's checklist and the pickers keep the spec's agency-then-name order.
- **The default while a write runs** (plan review A13). `useTaxActions` sends only the chosen row's `is_default` (the server clears the previous one in the same serialized write). While that write is pending, `buildTaxesView` takes `pendingDefaultId` (the write's target, `''` for Remove default) as the default; after it, the default is the row with `is_default`, and if realtime briefly shows two, the one with the latest `updated` (the server's swap stamps the new default last), ties by `compareNames`. Only `defaultRow` carries `isDefault` in the view, so the badge is never on two rows. A refused write clears `pendingDefaultId`, pbtsdb rolls the optimistic row back, and the picker's value (it follows `view.defaultRow`) returns to the stored default.

  - `parseRatePercent(text: string): number | null` — trims; accepts `^\d{1,3}(\.\d{1,4})?$` (an optional trailing `%` and spaces around it allowed); returns integer ppm by string arithmetic (whole × 10 000 + the fraction padded to four digits), never a float multiply; `null` for empty text, a fifth decimal, a sign, or a value over 100 (`100.0001`)
  - `ratePercentText(ppm: number): string` — `<whole>.<fraction>%` with trailing zeros dropped and no dot when the fraction is zero: 29 000 → `2.9%`, 88 750 → `8.875%`, 0 → `0%`, 1 000 000 → `100%`, 1 → `0.0001%`

  - `groupTax(taxableCents: number, componentPpms: readonly number[]): number[]` — `componentPpms.map(ppm => taxOn(taxableCents, ppm))` (each component rounded separately; the group's tax is their sum)
  - `groupPpm(componentPpms: readonly number[]): number` — the sum
  - Go: `taxOn(taxableCents, ppm int64) int64` and `groupTax(taxableCents int64, componentPpms []int64) []int64`, the same arithmetic with `int64`
