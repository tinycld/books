## Plan decisions (where the plan settles what the spec or phase 3 left open)

- **D1 — the toolbar's "⋯" rows.** `ResponsiveToolbar` folds a `custom` item into "⋯" as one row or as a `Menu.Sub`. Checkpoint 0 adds a third form of `ToolbarOverflow`, `{ rows: ReactNode }`: the item's own `Menu.*` rows, listed in "⋯" in place of the item. `ReportHeader` needs no `moreMenu`.
- **D2 — the second line of a menu row.** Checkpoint 0 adds `description?: string` to core `Menu.Item` (one muted line under the label, in the popover and in the sheet). The reference's `Menu.Custom` text row is not kept.
- **D3 — "Preparing…" when Export is folded.** Export is the last toolbar item, so it is the first to fold into "⋯" (a phone, a narrow window). While a file is prepared: the Export button, when it is in the row, is disabled and reads "Preparing…" (the spec); the export rows in "⋯" are disabled (reference `preparing-phone-*`); and the header's status slot (`ReportUpdating`, a live region) shows "Preparing…" at every width, so a reader whose Export is folded sees and hears that a file is on its way.
- **D4 — audit actions need a core migration.** `audit_logs.action` is a select; a value it does not list fails the save (`core/server/pb_migrations/2090000005_audit_logs_offboard_actions.js` says so). The spec's Behavior needs the audit rows. Checkpoint 1 adds one core migration that adds the values `report.export` and `report.email` to that select (no collection, no field). The human accepted this on 2026-11-16; the spec's Data section now names the migration. The lane does not take `exclusive` for it.
- **D5 — the engine's row cap.** A pivot, nest or layout run stops at `runLimits.rowCap` (5 000) rows with a `rowCap` or `nestCap` notice, so an export of such a report would be cut short. Checkpoint 1 adds `Request.RowCap int` to core's `reports.Request` (0: the default cap); the run endpoint never sets it; the export read sets it to the format's limit plus 1. The run endpoint, the spec, the result shape and the table do not change. A read that still reports `rowCap` or `nestCap`, or that holds more rows than the format's limit, is refused with the format's message.
- **D6 — the file name in the dialog.** The dialog shows the name before any request, so the client has a TypeScript `exportFileName` (`core/reports/lib/export-client.ts`). The Go `exportFileName` names every real file. `format-cases.json` holds a `fileNames` case list that both suites run, so the two cannot differ; an e2e compares the dialog's line with the name of the file the server sends.
- **D7 — what a row holds in a file.** All three formats apply the view's rule that a figure shows once (`visibleRows` in `core/reports/lib/rows.ts`): a group row that its own subtotal row follows has no figures, and a detail row's label column cell is not repeated. The first shown column is the label column: its cell is the row's label text.
- **D8 — an empty report.** PDF: the header and the view's empty text. Excel: the header block, the heading row, and the empty text in the first cell under it. CSV: the heading line only (the CSV has no page text).
- **D9 — the fixture.** There is no migration checkpoint and core cannot import a Books file, so the fixture's local types (`ExportFormat`, `ExportRequest`, `EmailRequest`, `EmailAnswer`, `EmailStatus`, `EmailFormValues`) are replaced by core's exported types in checkpoint 5, the first Books checkpoint. No seed wiring: the seeded ledger already fills the shipped reports.
- **D10 — spark 1 (finished-document page)** is the PDF's first page. No screen shows it, so gate 2 has no shot of it: checkpoint 2 pins it in Go tests on the page HTML (logo, brand color, centered header) and writes one sample PDF to `docs/plans/report-exports-evidence/cp2/` in books for the eval gate.
- **D11 — core-owned behavior is tested in core.** The menu, the downloads, the dialog and every refusal are core code over any report: core e2e drives them on `salesstub`. Books e2e (checkpoint 5) pins what is Books': the names and content of files made from Books' shipped reports, and the phone path on a Books report.
- **D12 — the email status.** `GET /api/reports/email-status` is read with React Query when the report view mounts. Until it answers, "Email report…" is disabled with no second line. When the read fails, the item is enabled and the send's own refusal covers the case.
- **D13 — the toast for two addresses.** The spec's toast is "Report sent to <first address>" or "Report sent to <first address> and <n> others". With two addresses the plan writes "and 1 other" (singular), not "and 1 others".
- **D14 — `saveFile` has no test of its own.** Its web path is proven by the download events of checkpoint 3's e2e. Its native path (the share sheet) is not executed by any gate; the ledger's final review says "native: not executed".
- **D15 — where the formula guard is.** The leading apostrophe is the CSV's rule only (the spec lists it under CSV). An Excel text cell is a string cell (`SetString`), which a spreadsheet never runs, so its text has no apostrophe. `RawCell` gives the plain text; `writeCSV` adds the apostrophe with `csvGuard`.
- **D16 — the mail capture log in dev.** The spec's status is true "when the server's mail capture log is on (dev and e2e)". `mailer.CaptureLogOn()` is true when `TINYCLD_EMAIL_LOG` is set (e2e) or when the server runs with `--dev` (`devAutoLog` in `core/server/mailer/mailer.go`, where `DefaultSender` is a `LogSender`).

Where the goal is "this control is offered only when it can work", the test asserts each state of that one control (for example: invalid, offline, empty). The rules that a pure function decides (the report states that disable Export, where Export is offered) are also pinned state by state in a unit test of that function.

**Gates:** 1 · 3 (nothing renders)

**Spec:**
- Export is offered to every reader who can open the report. The file holds what that reader's run returns, never more.
- The server names the file semantically from the report's name and its date: `<report name>-<date part>.<pdf|xlsx|csv>`. The name is the report's saved title (not its id or key), in lower case, words joined by `-`, characters other than letters, digits and `-` removed (letters of any script are kept), at most 80 characters. The date part is the report's period (`2026-01-01-to-2026-11-15`), the as-of day of an as-of report (`as-of-2026-11-15`), or the reader's day for a report with no date param. Example: `profit-and-loss-2026-01-01-to-2026-11-15.pdf`. The download, the email attachment and the dialog's attachment line use the same name.
- UTF-8 with a byte order mark, comma separated, CRLF line ends, quoted by RFC 4180.
- Line 1 holds the column headings: the row-label column first, then every shown column in view order.
- Then one line per row, with every group open, in report order: group, detail, opening, subtotal, computed and total rows.
- Values are raw: money as a decimal number with two places, a period and a leading minus, no symbol and no thousands separator; the number format options do not apply; percent as a number (12.5); a date as `YYYY-MM-DD`; a date-time as `YYYY-MM-DD HH:MM` in the reader's zone; a bool as `TRUE` or `FALSE`; a bucket label in words, as shown.
- A money column whose rows carry different currencies is followed by a column "<heading> currency" with each row's ISO code.
- A text cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading apostrophe, so a spreadsheet does not run it as a formula.
- No header lines, no notices, no page text.
- The server reads the whole report, page by page, as the reader.
- A CSV or Excel file of more than 50 000 rows is refused: "This report has more than 50,000 rows. Narrow the period."
- An export that takes longer than 60 seconds is refused: "The report took too long to export."
- No file is ever cut short without a refusal.
- The routes take a signed-in session only. An OAuth token, a signed-out request and a disabled account are refused. A reader who cannot open the report gets "You no longer have access to this report".
- Every download and every sent email writes one core audit row: action `report.export` or `report.email`, the report's id and title, the format, the row count, and for an email its recipients. It shows in Settings → Audit log.
- Data: "The file name comes from one Go function (`exportFileName`) used by download and email; a Go test covers period, as-of, no-date, non-Latin and over-long titles." and "The text of each cell comes from `export_format.go`. `format-cases.json` lists cells, labels, headings and periods with their expected text; the vitest suite runs it against `lib/format.ts` and the Go suite against `export_format.go`, so the two cannot drift."
