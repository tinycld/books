## Decisions that apply to every checkpoint

- **No draft bill payment (human decision 2026-11-15, option A).** `books_bill_payments.status` is the select `posted | void`. The client creates each payment with `status: 'posted'` and its lines in one pbtsdb batch. The server's **create request hook** on `books_bill_payments` (`server/bill_payments.go`, `bindBillPaymentCreate`) owns the post: (1) when `e.App.TxInfo() == nil` (a single REST create, not a batch) it refuses root `Select at least one bill to pay.` before `e.Next()`, so nothing is stored; (2) it calls `stampActor` for `posted_by`; (3) `e.Next()` runs the model create (its guard, inside `serialized`, checks the header and sets the tx mark `books.billpayment.creating.<id>` with `setTxMark`), and every later batch operation runs inside it (in a batch, operation N+1 runs inside operation N's `e.Next()`, third_party/pocketbase/apis/batch.go `process`); (4) after `e.Next()` returns with no error, it runs `e.App.RunInTransaction(func(tx core.App) error { return postBillPayment(tx, rec, time.Now()) })` (in a batch this joins the batch transaction; `serialized` cannot be used here: it takes a model `*core.RecordEvent` and calls `e.Next()` itself), where `rec` is the payment re-read with `tx.FindRecordById` (no line → `Select at least one bill to pay.`); (5) a `defer` clears the mark with `clearTxMark` on every path. The `bindSalesDocDeferral` pattern (`server/sales_document_deferral.go`). A Go write with no request (tests that call `app.Save`) never posts: Go tests write bill payments through `batchAs` (as `server/bill_batch_test.go` does).
- **Line writes.** A `books_bill_payment_lines` create is admitted only while its payment carries the creating mark (`hasTxMark`) and is not yet posted (`number` empty); update and delete are refused to a person always. A bill correction moves lines under `markMovingLines(tx, billBalanceKind, …)` (server only). Line texts below.
- **Batch order and refusals (spec §9).** The last payment in a batch posts first (its `e.Next()` returns first). The client writes the vendors in **reverse** display-name order (vendor `display_name`, then vendor id), each payment followed by its lines, so the numbers (allocated at post) follow display-name order: the first vendor by name gets the lowest number. A refusal inside a payment's post is raised by that payment's own operation, so PocketBase's `failedIndex` and pbtsdb's `BatchMutationError` name that payment (`refusedRecordId`, `lib/batch-refusal.ts`); a line guard refusal names the line. The client maps both through its write plan (`lib/pay-bills-plan.ts`) to a bill row or a header field. **The batch answer holds each payment as created, before its post** (`batch.go` writes a create's JSON before `next` runs), so pbtsdb lands rows with `number: ''`, `total: 0`, `entry: ''`; the client never reads the numbers from the landed rows: after the batch resolves it awaits the pbtsdb collection's `reload()` on `books_bill_payments`, then reads the numbers of the plan's ids with `queryOnce` (checkpoint 2 Do 7). The e2e toast assertions pin this.
- **Starting check numbers (spec §3.2).** In display-name order, vendor k (from 0) gets `String(BigInt(start) + k)` as `reference_no` — the number is at most 9 digits so `Number` is exact too; a leading zero is not kept (`"0099"` + 1 → `"100"`, plan decision: the server stores plain numbers). Empty Starting check no. → every `reference_no` is `''`.
