## Decisions that apply to every checkpoint

- **The transfer sequence row id is `booksseqtransfr` (15 characters), not `booksseqtransfer`.** A PocketBase base collection's default `id` field is a text field with `Min: 15`, `Max: 15` and the pattern `^[a-z0-9]+$` (`/Users/nas/tmp/tinycld/books-reports/tinycld/third_party/pocketbase/core/collection_model.go`, `initIdField`). `booksseqtransfer` has 16 characters, so the migration's `app.save` would refuse the row. `booksseqtransfr` keeps the `booksseq<type>` pattern of `booksseqjournal` (15) inside the limit. This is the only change to a name the spec gives.
- **Resolved reference ambiguities (driver decisions, 2026-11-04).**
  1. The back link is the journal entry screens' `EntryBackLink` (`components/entries/EntryHeader.tsx`), whose label comes from `useBackToEntries` (`hooks/useBackToEntries.ts`): "Journal entries" (or "Register" when the screen was pushed from a register, as for journal entries). Its press goes through `EntryLeaveContext`, so the form's back link asks before it drops edits.
  2. `VoidDialog` (`components/entries/VoidDialog.tsx`) is used as it is: title `Void TR-3?`, body "A reversing entry is posted in the original period. The number is kept.", confirm `Void entry` (`void-confirm`), through `useEntryDialogs` (`hooks/useEntryDialogs.ts`).
  3. The From and To pickers show the placeholder `Choose an account` while nothing is picked and no stored account needs a trigger label.
  4. A saved draft's More menu sits after Post on wide screens and holds `Delete draft`; on a phone More holds `Post & new`, then `Delete draft`. A new form has no More on wide.
  5. The error state has Retry only (no back link).
  6. The read view's actions sit in the sticky bar drawn by `EntryReadOnlyActions` (`components/entries/EntryReadOnlyActions.tsx`): wide Void then Edit buttons in `entry-actions`; phone `entry-more` (Void) then `entry-edit`.
- **Amount text.** Blank or not well-formed text (`isWellFormedMoney`, `lib/money.ts`) is "Enter an amount like 1,234.50". Well-formed text that `parseMoney` cannot hold (above 2^53-1 cents) or above `MAX_TRANSFER_AMOUNT` (10^15 cents, the server's `maxAmount` in `server/posting.go`, drift-tested) is "The amount is too large". Zero or a negative amount is "Enter an amount more than 0". On blur a valid amount is rewritten by `formatAmountOnBlur` (`lib/entry-lines.ts`), whose output is the currency form (`$1,234.50`); the reference shots show typed text before a blur, and gate 2 does not count that difference. The header figure is `—` for blank, malformed or not-positive text, `Too large` (`TOO_LARGE_TEXT`) for too large, else `formatMoney`.
- **Memo length counts code points.** PocketBase counts a text field's length in runes (`third_party/pocketbase/core/field_text.go`, `len([]rune(value))`), so the schema counts `Array.from(memo).length`, not `memo.length`.
- **Messages** (exact; the client copies are unit-tested against the fixture or drift-tested against the Go source):

  - server (`server/transfers.go`, `server/entries.go`; PocketBase keeps a message that already ends with a period): `A transfer has two lines: the account the money comes from and the account it goes to.` · `Line 1: a transfer moves money out of this account, so it takes a credit.` · `Line 2: a transfer moves money into this account, so it takes a debit.` · `Line 2: choose an account other than the one the money comes from.` · `Line %d: %s cannot be used in a transfer. - **Server order of checks.** `postEntry` runs `checkAutoReverseDate`, then `validateLines`, then `checkTransfer`. So a transfer line on an inactive account is refused by `validateLines` first (`Line n: account <name> is inactive.`), which is still a "Line n" refusal the form puts under its field. With exactly two balanced lines whose line 1 is a credit, line 2 is always a debit, so `Line 2: … takes a debit.` cannot be reached after `validateLines`; `checkTransfer` keeps it as a defensive check, and only its wording is tested (the TS drift test). A one-line transfer is refused by `validateLines` (`A journal entry needs at least two lines.`); the two-line refusal is tested with three lines.

**Decisions (loop, 2026-11-05):**
- **Two phases, one decision per key.** The capture binding takes a key typed in a text field (the matcher's `inInput` gate keeps every non-`allowInInputs` shortcut out, so typing is unchanged) and a key held with Ctrl, ⌘ or Alt. The bubble binding takes every other key (no modifier or Shift only, outside a text field), exactly as today. Reason: react-native-web stops (a) every key in a `TextInput` and (b) Enter, with any modifiers, and Space on a Pressable. A plain Enter or Space on a button is the button's own key; and core menus push no shortcut scope on wide web (only `Dialog`, `Sheet` and the search palettes render `LayerEscape`), so a capture-phase plain key would let a screen's `j` or `ArrowDown` take a key the open menu answers (`handleMenuKeyDown` stops the arrows, Home, End and typeahead letters for that reason). A plain key outside a text field reaches the bubble binding unless the focused element stops it, as today: Enter and Space press a button, the menu keeps its keys, `g i` sequences work.
- **Escape yields to the layer.** `layerTakesEscape` is `topLayer()?.dismissOnEscape === true`. `keyPhase` then returns `null` for Escape, in and out of a text field, with or without modifiers, so neither binding feeds it. The window capture listener always runs before layer-stack's document capture listener (DOM capture order is window, then document), so this yield is what keeps layer-stack the only Escape handler while a layer is open. With no such layer, Escape follows the rule above (a text field: capture; elsewhere: bubble).
- **Consumed.** In capture a consumed key gets `preventDefault()` and `stopPropagation()`, so the focused element never sees it (a Pressable starts no press, a field types nothing); in bubble only `preventDefault()`, as today. "Consumed" is the matcher's own answer: a shortcut ran, or the key continues a registered sequence (no sequence with a modifier or `allowInInputs` is registered today). An unmatched key, or one whose `when()` is false, is not touched.
- **Facts once per key.** The capture handler builds `KeyFacts` (key, modifiers, `isInputKeyEvent`, `layerTakesEscape`) once and keeps them in a module `WeakMap` keyed by the event; the bubble handler reads the same facts, so a handler that moves focus or opens a layer during the dispatch cannot make one key fire twice or not at all.
- **Help floor.** `open()` records `nextScopeId()` as `scopeFloor`. The overlay's `LayerEscape` mounts after that, so its `modal` entry has an id at or above the floor; `helpGroups` judges each shortcut against `topScopeEntry(scopeFloor)`, the stack without the overlay's entry. A dialog the screen already had open is below the floor, so its keys are listed. The overlay's own "Close" (`LayerEscape`, group General) is no longer listed (its scope is the overlay's); `core.closeHelp` is in group Help, which stays hidden. The memo depends on the registry map and `scopeFloor`.
- **Native and Android: no change.** iOS: `KeyboardExtendedView` wraps the app and receives presses through the UIKit responder chain (`react-native-external-keyboard` `RNCEKVViewKeyPress.mm` `pressesBegan` hands every press to its handler and then `[super pressesBegan:]`); no JS handler stops a key on the way, and a React Native Pressable takes no key focus on iOS (checkpoint 8, gate 3 B: `enableImperativeFocus` is off). Android: the provider is a passthrough with no key capture. Neither has the web gap; neither file changes.
- **An open menu keeps the old path (gate 3 A BLOCK 2, B 1).** Core menus and popovers push no shortcut scope, so the screen's scope stays on top under them. Before this checkpoint a menu's search field (a `TextInput`) and the focused trigger (a Pressable) stopped ⌘↵ and the other modified keys; a capture-phase dispatch would run the screen's Post under an open "Transfer from" menu. So while the top open layer is not modal (`menuOpen`: `topLayer()` set and `isModal` false), `keyPhase` sends every key except a yielded Escape to the bubble binding, exactly the path before this checkpoint. Dialogs and sheets are modal layers and push the `modal` scope, which mutes the screen's keys while their own `modal` shortcuts still fire from their fields. The search palettes push the `modal` scope but join the layer stack as non-modal layers, so they take the menu path (fix review 1 NOTE 1).
- **Global shortcuts keep the old path from a text field (fix review 1 NOTE 3).** calc registers ⌘F, ⌘⇧H, ⌘G, ⌘⇧G as `global` `allowInInputs` shortcuts gated only on calc's own store, and calc stays registered after the user leaves it (`freezeOnBlur`); read in the capture phase they would take ⌘F from a text field in every package (calc's find opens on the hidden sheet, the browser's find is cancelled). A react-native-web field always kept those keys before. So for a key typed in a text field (no menu open) the capture binding feeds only shortcuts of a scope (`only: 'scoped'`), and the bubble binding feeds only `global` ones (`only: 'global'`), the path they had before: a react-native-web field still stops them, a contenteditable surface still lets them through. Every other key feeds every shortcut in its one phase.
- **What `allowInInputs` now reaches on web.** Shortcuts registered with `allowInInputs: true` now fire from a react-native-web text field, as their registration says: mail compose ⌘↵ (Send) from the To and Subject fields; calc ⌘F, ⌘⇧H, ⌘G, ⌘⇧G (gated as today; the find box's own `fieldShortcut` handler no longer sees them, so each still runs once); a `modal` Escape that no core layer owns (Books `RecordSurface`). **Decisions (loop, 2026-11-05):**
- **Scopes.** The form registers in a `compose` scope and the read view in a `thread` scope, each from its own `useShortcutScope` in the same component that registers (core docs/keyboard-shortcuts.md: "`useShortcutScope` and the registration belong in the same component"). Core dialogs and sheets render `LayerEscape`, which pushes a `modal` scope over them, so no form or read-view key fires while one is open. Core menus and popovers push no scope (core checkpoint 9, Decisions "An open menu keeps the old path"): while one is open, core sends every key to the bubble phase, so the menu's search field and its focused trigger still stop ⌘↵ and the other form keys, and a key pressed on a focused menu row still reaches the form. With any layer open core's layer stack alone takes Escape, so Escape closes only that layer. A draft whose post is unconfirmed shows the read view over the hidden form (`DraftScreen`, `TransferDraftScreen`); the read view's scope is pushed after the form's, so the read view holds the keys.
- **Availability** (`formKeyAvailable`): Cancel — not pending (the Cancel button is disabled while pending). Save draft, Post, Post & new — not pending and writes available (`ServerActionButton` / `useServerActionState`). Delete draft — a saved draft (`hasDraft`) and not pending (the More trigger is disabled while pending). On a phone Post & new sits in More and is still available. The form mounts only for a writer (the new route shows `transfer-no-access`; a reader's draft opens read-only), so it has no `canWrite` input. `readKeyAvailable`: `actions.includes(action)` and not busy (`isVoiding` / `isReversing`); a reader's `entryActions` is `['open']`, a void entry's is `['open']`, a transfer's never includes `reverse`.
- **Read keys follow the offered actions (human decision 2).** `readShortcuts` builds a shortcut only for a read key whose action the view offers when it registers (`offered`), so core's ⇧? list (which lists every registered shortcut of the active scope and does not read `when`) shows R only where Reverse is offered, and the same rule keeps E and V out of the list for a reader or a void entry. `useReadViewShortcuts` memoises on the offered read keys, so the keys re-register when the actions change (after a void or a reversal); `when` still reads the actions and `isBusy` at press time.
- **⌘S always taken.** Save draft's shortcut has no `when`: while the form holds the keys (no dialog, sheet or menu open) core consumes ⌘S (core's web provider calls `preventDefault` on a consumed key, from a text field too), and its `run` saves only when `formKeyAvailable('saveDraft', …)`. Every other key uses `when`, so an unavailable ⌘⌫ keeps the text field's own delete-to-line-start.
- **State read at press time.** The hooks keep the latest state and handlers in refs assigned during render (as `RecordSurface`'s `onLeaveRef`), and the shortcut array is memoised on `group`, a `useId` instance and (read view) the offered read keys, so an ordinary render never re-registers.
- **Descriptions** (core's overlay sorts by description): `Post`, `Post & new`, `Save draft`, `Cancel`, `Delete draft`, `Edit`, `Void`, `Reverse`. Groups: `Transfer` (transfer form and read view), `Journal entry` (journal form and read view). Ids (gate 3 B 7, as built): `books.<group-slug>.form.<instance>.<action>` and `books.<group-slug>.read.<instance>.<action>`, with `<group-slug>` from `shortcutGroupSlug` (the hook passes `books.<group-slug>.form.<instance>` as `id`, and the lib appends `.<action>`).
- **Autofocus only when ready.** `TransferForm` mounts only after access, settings and accounts are ready (new route `TransferLoading`, `TransferScreen` held draft, `TransferReplaceForm` held original), so the From trigger never mounts disabled; `SelectInput` focuses once at mount (web only; nothing on native). Post & new replaces the route (`useTransferAfterSave`, `TransferDraftScreen`), which mounts a fresh form. The journal Date gets `autoFocus` only when `Platform.OS === 'web'` and `useBreakpoint() !== 'mobile'` (a wide browser window, tablet width included), never on iOS or Android and never the Auto-reverse date (human decision 1).
- **Text fields on web (settled by core #436).** Core now reads a key typed in a text field in the capture phase and offers it to scoped shortcuts, so the form keys (`allowInInputs`) fire from Amount, Date, Memo and the journal cells, and the field never sees a key a shortcut takes; E, V and R (no `allowInInputs`) still do nothing there. The first attempt's deferral is closed with no Deferrals entry, and the e2e presses the form keys while a text field or the From trigger has focus (no title clicks), which proves the core fix through Books.
