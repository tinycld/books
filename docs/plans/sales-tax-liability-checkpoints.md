## Plan decisions (where the plan departs from the spec's letter, and why)

- **D1 — shared October.** The seed already posts taxed invoices and sales receipts in October 2026 under Denver combined (`invoice-form-fixture.ts` `INVOICE_SEED_IDS`, `sales-receipt-form-fixture.ts` `SALES_RECEIPT_SEED_IDS`), and other specs may edit or void them on the shared e2e DB. So the e2e never asserts the fixture's pinned totals (`SALES_TAX_LIABILITY_TOTALS`, 291.74) or an exact figure of Colorado state, RTD transit or Denver city. It asserts exact figures only for the rates that no other seed or spec charges (`SALES_TAX_LIABILITY_OWN_RATES`: Old county rate, Adams County, Retired rate, Denver lodging, Exempt food sales (state), the Scientific and Cultural Facilities District rate), computed from the fixture, and relations inside one snapshot for the rest (an agency total = the sum of its rate rows' tax; Total = the sum of the agency totals). `TestSalesTaxLiabilityTotals` pins exact totals over a book of its own.
- **D2 — the void e2e posts its own invoice.** Spec §5 asked the void e2e to void a seeded invoice. A retry, or a second run on the same DB, would find it void already. The test creates an agency and a rate (Sales tax page), posts an invoice under that rate dated today, and voids it; the seed itself posts and then voids the fixture's void document (`stlinv000001046`), so a dev book still shows a void drop out. Spec §5 says so (edited in phase 4).
- **D3 — phone layout.** Phase 3 pass 2 found that four figures do not fit one 390 px line, so the shipped spec carries `display` (`SALES_TAX_LIABILITY_DISPLAY`: label on line 1, Gross total · Non-taxable on line 2, Taxable amount · Tax amount on line 3; `oneLine.minWidth` 600px). Spec §3 now reads "label, then the figures on two lines" and §5 lists the display (edited in phase 4). Checkpoint 2 ships it; checkpoint 3 pins it at 390 and 375 (lesson 32).
- **D4 — core-owned behavior.** Loading, error and Retry, Customize, sort, copy link and Save as are core's view, driven by core e2e (`reports-view.spec.ts`, `reports-failure-states.spec.ts`, `reports-share.spec.ts`). Books pins what Books owns: its sources and spec (Go), its share (`server/report_shares.go`, unchanged: it shares every `books.*` shipped report), the figures, the phone layout and the entry points. Gate 2 compares `loading-*` and `error-*` nowhere: they are core's view over a static model, captured in phase 3 only.
- **D5 — help in two steps.** The help topic is written in checkpoint 4 (the last checkpoint that does not wait on tinycld#475) with every point of spec §3's Help bullet except opening a document; checkpoint 5 adds that sentence with the behavior. A user can read everything the build offers at each step.
- **D6 — the kind label.** `books.sales_documents.kind` is a constant select per part (invoice "Invoice", sales_receipt "Sales receipt"). A formula reads a select's value, not its label, so the detail label writes the words with `if(eq([document, kind], "invoice"), "Invoice", "Sales receipt")`.
- **D7 — gate 2 figures.** The reference is drawn from the fixture alone; the built report also holds the other seeded October documents (D1). Gate 2 judges the arrangement (order, indents, blank sales cells above the rate level, the phone lines), not the numbers.
- **D8 — one Go book for both document kinds.** No Go test env holds posted invoices and sales receipts together (`newPostingEnv` binds the invoice kind only; `receiptEnvOn` makes its own accounts and agencies, which collide with `newPostingEnv`'s). Checkpoint 1 adds `newSalesTaxEnv` (`server/sales_tax_env_test.go`): `newBooksApp`, `registerLedger`, `registerSalesDocGuards` for `invoiceKind` and for `salesReceiptKind`, `bindSalesDocHosts` (it loads both hosts), then `receiptEnvOn` (accounts 1000/1010/1100/1200/3900/4000/4100, the Denver combined group over three agencies, Harborview Dental, the products). Invoices on it are made with `newInvoice(app, env.customer, fields)` + `mkInvoiceLine`, receipts with `env.mkReceipt` + `mkReceiptLine`. Every Go test of this run that posts documents uses it.
- **D9 — the button lives in `TaxesPage.tsx`.** Spec §2 names `screens/taxes.tsx`; that screen only renders `TaxesPage` (`components/taxes/TaxesPage.tsx`), whose `Header` holds the title and actions, so the button goes there.
- **D10 — groups on hidden link columns.** `reports.Group.Col` names a spec column (`core/server/reports/spec.go`), so the spec has two hidden columns, `agencyKey` (the tax line's `agency` link) and `rateKey` (its `component` link), as the Balance Sheet groups on hidden `side`/`cls`/`knd` (`server/report_balance_sheet.go`). Name order comes from the spec's `Sort` keys over the group records (`server/report_general_ledger.go`'s `Sort`). The result shows only the five visible columns.

**Sizing:** 5 checkpoints after checkpoint 0 (tax line snapshot and seed; the report by agency and rate; documents under a rate; the Sales tax page button and help; document rows opening their document).
