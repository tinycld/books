## Plan decisions (where the plan departs from the spec's letter, and why)

- **D1 — Name width (phase 3 pass 2 open point).** Core shares a line's spare room first by what each column lacks of its natural width (`core/reports/lib/table-lines.ts` `shareWidth`), so at the one-line widths a long Name (~180–200 px) drew wider than Description (~160–170 px) despite `description.flexGrow: 2`, against spec §3 ("Description takes the most of the spare room"). Decision: the Journal spec's `display.columns.name` is `{ minWidth: "16ch", maxWidth: "16ch" }` — Name is always 16 characters wide: an ordinary customer or vendor name (about 16 characters, spec §3) stays whole, a longer one ends in an ellipsis, and core's `applyMax` (`core/reports/lib/column-measure.ts`) caps Name's natural width, so its lack and its grow stop at 16ch and the spare room goes to Description (and Account). No core change: the driver, for the human, named this route ("a Name maxWidth in the books spec, no core change"). Weighting core's lack share by grow would change the fit of every report (Trial Balance, General Ledger, core's own), a second core extension the design gate did not approve. The price: a name longer than about 16 characters ends in an ellipsis at every width, also at 1280; spec §3 "Every width fits" now says so, and Description is still the column that narrows first (Name never goes under 16ch). Spec §3, §5 and the fixture's `JOURNAL_DISPLAY` say the same (edited in phase 4). The reference shots `populated-1024-*` / `populated-1280-*` were taken before this decision and show Name wider than it ships: gate 2 judges the Name and Description widths against spec §3/§5, not against those shots.
- **D2 — e2e count.** Spec §7 lists 11 items, 12 runs (item 1 desktop and phone). A screen adds at most 12 runs and a checkpoint at most 6. Item 1's phone run folds into item 9 (the phone run opens the Journal from the Books menu drawer, the one phone-only path of item 1). 11 runs, numbered in this plan 1–11 in checkpoint order: checkpoint 1 has spec items 1–6 (plan 1–6), checkpoint 2 spec items 9 and 10 (plan 7 Phone, 8 Tablet and desktop widths), checkpoint 3 spec items 7, 8 and 11 (plan 9 Long block, 10 Live, 11 Empty).
- **D3 — long block page seam.** Spec §7 item 7 says scrolling "loads the rest of the first block, then the second block". With J1 a page holds up to 200 rows counting the group, detail and subtotal rows: the first block of the seeded long section (`GENERAL_LEDGER_LONG_SECTION`, two entries of 131 lines: 130 "Daily sweep" lines and one offset) is 133 rows, so the first page holds the whole first block and ends inside the second. Item 7 asserts that seam (the second block has fewer than its 131 lines and no block total on the first answer; scrolling loads its other lines, its block total, then the Total row) — the behavior of spec §3 "A large period", "A block longer than one page continues on the next page".
- **D4 — exclusive released (human, after the design gate).** The lane does **not** take `exclusive` for J1 ("the others will not conflict"). The core merge of J1 still needs the human's approval: checkpoint 0 stops before the merge.
- **D5 — core-owned behavior.** Customize, the loading/error/timeout/no-access states, Copy link, Save as, the fold toolbar and the empty state's text with its "Show this fiscal year" action are core's view, driven by core e2e (`reports-view.spec.ts`, `reports-failure-states.spec.ts`, `reports-share.spec.ts`). Books pins what Books owns: its spec (Go tests), its share (`server/report_shares.go`, unchanged), the folding of its open blocks (e2e 5, because the spec opens every block), its sort keys (e2e 6), its topics (Go + e2e 8) and its empty run (Go + e2e 11).
- **D6 — record paths.** `rec(group string, names ...string)` reads a to-one path of the group's record (core record leaves bind a to-one path, `core/server/reports/record.go` `bindRecordPath`), so the block heading reads `[reverses, number]` through `rec("byEntry", "reverses", "number")`. Existing two-argument calls keep their JSON.
